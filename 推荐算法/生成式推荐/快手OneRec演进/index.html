快手 OneRec 演进

OneRec 将推荐从“召回候选、逐条打分、逐级筛选”改写为“读取用户历史、生成一个推荐 Session”。围绕这条主线，快手先后完成了 V1、V2、OneRec-Think、OpenOneRec 和 OneReason，模型的重点也从统一召回与排序，逐步转向计算效率、真实反馈、基础模型和推荐推理。

1. OneRec要解决什么问题

1.1 多阶段级联系统为什么越来越重

工业推荐系统通常由召回、粗排、精排和重排组成。召回从百万乃至十亿级物品库中找出数千个候选；粗排继续压缩候选；精排综合用户、物品、上下文和行为序列，预测点击、观看时长、互动等目标；重排再处理多样性、新鲜度和业务约束。

对用户 uuu、候选物品 iii 和上下文 ccc，传统排序模型学习的是一个打分函数：

su,i=fθ(u,i,c).s_{u,i}=f_\theta(u,i,c). su,i​=fθ​(u,i,c).

系统先对每个候选独立或近似独立地计算分数，再通过融合公式和重排规则得到最终列表。这个方案非常成熟，但模型越做越复杂后，四个问题逐渐突出。

第一，各阶段拥有不同的样本空间和优化目标。召回追求 Recall，粗排关注低成本筛选，精排预测 CTR、观看时长等指标，重排优化列表体验。前一阶段漏掉的物品，后一阶段没有机会补救；每个局部模型都变好，也不保证最终列表最优。

第二，系统中存在多套特征、Embedding、缓存和服务。大量资源消耗在模型之间的通信、特征搬运和中间结果存储上，真正用于高精度矩阵计算的比例有限。

第三，Point-wise 打分天然围绕单个候选展开。推荐结果却是一个有顺序的列表：前面已经推荐了什么，会影响后面的内容选择。传统系统往往把这部分交给规则或单独的重排模型。

第四，碎片化的小模型和小算子不容易沿用 LLM 的 Scaling 路线。增加参数不一定增加有效计算，强化学习也很难跨越多阶段链路直接作用于最终推荐结果。

图1：传统推荐逐阶段筛选候选，OneRec将用户历史转成Token后直接生成推荐Session。本文绘制。

1.2 把推荐改写成序列生成

OneRec 的出发点很直接：既然最终需要的是一组有顺序的物品，就让模型直接学习这组物品的联合分布。

设用户历史为 HuH_uHu​，当前上下文为 CCC，推荐 Session 为 S=(i1,i2,…,iK)S=(i_1,i_2,\ldots,i_K)S=(i1​,i2​,…,iK​)，生成概率可以写成：

Pθ(S∣Hu,C)=∏t=1KPθ(it∣Hu,C,i<t).P_\theta(S\mid H_u,C) = \prod_{t=1}^{K} P_\theta(i_t\mid H_u,C,i_{<t}). Pθ​(S∣Hu​,C)=t=1∏K​Pθ​(it​∣Hu​,C,i<t​).

第 ttt 个物品的生成条件包含用户历史、场景上下文，以及前面已经生成的物品 i<ti_{<t}i<t​。列表内的相关性、互补性和重复问题由同一个生成过程建模，不再完全依赖事后规则修补。

因此，OneRec 的目标并非单纯把召回模型换成生成式召回，而是建立一个新的推荐主干：统一 Token 表示，使用规整且可扩展的 Transformer 计算，把监督学习和偏好对齐都施加到最终推荐序列上。

2. OneRec的整体技术框架

OneRec 系列跨越了多种架构：V1 使用 Encoder–Decoder，V2 改成 Lazy Decoder-Only，OpenOneRec 和 OneReason又建立在 Qwen 系列 LLM 上。具体模块一直在变，但它们共享一条数据流：用户与物品表示 → Token 化 → 自回归生成 → 偏好对齐 → 推荐 Session。

图2：OneRec系列的统一技术骨架。各版本的具体Backbone和训练算法不同。本文绘制。

2.1 输入：用户历史不是一串裸ID

OneRec 的用户侧输入来自有效观看、点赞、关注、收藏、分享等行为。除了视频本身，工业模型还会使用用户画像、行为类型、时间、位置、场景以及多尺度历史序列。高基数的 item_id、author_id 等离散特征由 Embedding 表示，动作、时间和位置特征则通过独立 Embedding 或投影层注入。

经过拼接、分组或投影后，用户输入可抽象为：

Xu∈RL×d,X_u\in\mathbb{R}^{L\times d}, Xu​∈RL×d,

其中 LLL 是上下文 Token 数，ddd 是模型维度。V1 技术报告进一步把用户行为组织成 User、Short-term、Periodical 和 Long-term 等多尺度路径，再由 Encoder 统一建模。V2 的 Context Processor 接管了这部分工作，OpenOneRec 则把文本 Token 与 Itemic Token 直接放进 LLM 上下文。

2.2 物品表示：一个物品由多个Token生成

如果为每个视频注册一个独立 Token，物品库扩大时，词表和输出层会同步膨胀；新物品还需要不断修改词表。OneRec 使用层次化 Semantic ID 表示物品。设视频的多模态向量为 eie_iei​，残差量化在第 lll 层选择码字 czl(l)c_{z_l}^{(l)}czl​(l)​：

zl=arg⁡min⁡k∥r(l)−ck(l)∥22,r(l+1)=r(l)−czl(l),z_l=\arg\min_k\left\|r^{(l)}-c_k^{(l)}\right\|_2^2, \qquad r^{(l+1)}=r^{(l)}-c_{z_l}^{(l)}, zl​=argkmin​​r(l)−ck(l)​​22​,r(l+1)=r(l)−czl​(l)​,

初始残差 r(1)=eir^{(1)}=e_ir(1)=ei​。最终，一个视频由 (z1,z2,…,zM)(z_1,z_2,\ldots,z_M)(z1​,z2​,…,zM​) 表示，例如 <a_9><b_7><c_1>。前面的 Token 表达较粗粒度的簇，后面的 Token 继续量化残差。

技术报告中的 Tokenizer 还先对多模态表示注入协同信号：内容相似且被相似用户消费的视频应当靠近，只有视觉相似但消费关系不同的视频应当区分。这样得到的 Semantic ID 同时携带内容语义和协同关系。

OpenOneRec 将这类离散物品表示称为 Itemic Token，并进一步强调它是一种独立于自然语言的“物品模态”。自然语言负责表达语义和推理，Itemic Token 负责精确指向物品，两者通过预训练对齐。

2.3 Backbone：从历史上下文生成推荐Session

模型先读取用户历史，再自回归生成目标物品的多个 Semantic Token。一个物品生成完毕后，已生成结果继续参与后续预测，直到形成完整 Session。训练仍采用标准 Next Token Prediction：

LNTP=−∑t=1Tlog⁡Pθ(yt∣Xu,y<t).\mathcal{L}_{\mathrm{NTP}} = -\sum_{t=1}^{T}\log P_\theta(y_t\mid X_u,y_{<t}). LNTP​=−t=1∑T​logPθ​(yt​∣Xu​,y<t​).

这里的 yty_tyt​ 可以是物品 Semantic Token，也可以是 OpenOneRec、OneReason 中的自然语言 Token。生成式建模的价值就在于这个统一接口：视频推荐、物品理解、兴趣总结和推荐解释都能写成条件序列生成。

2.4 偏好对齐：奖励最终生成的列表

仅靠 NTP，模型学到的是日志数据中“出现过什么”。推荐还关心用户是否真正喜欢、是否愿意持续消费，以及列表是否符合业务约束。因此，OneRec 系列逐步引入三类对齐信号：

  • V1 原始论文用 Reward Model 给 Beam Search 生成的 Session 打分，选择最好和最差结果组成偏好对，再做 DPO；
  • V1 技术报告形成更完整的 Reward System，并使用 GRPO/ECPO 等工业后训练方法；
  • V2 将真实曝光后的观看时长和显式负反馈接入强化学习，减少只优化代理 Reward Model 带来的偏差。

最终，系统形成闭环：模型生成物品，物品被曝光，用户行为转成新一轮奖励和训练样本。

3. OneRec系列的演进地图

OneRec 并不是严格按 V1、V2、V3 顺序发布。2025 年 2 月的原始论文和 6 月技术报告共同构成 V1 路线；OneRec-Think 是显式推理分支；OpenOneRec 面向开放基础模型；OneReason 则继续解决推荐推理问题。

4. OneRec-V1：统一召回与排序

4.1 Encoder–Decoder与Sparse MoE

OneRec 原始论文的模型接近 T5。Encoder 使用 Fully Visible Self-Attention 编码用户行为序列，Decoder 先通过 Causal Self-Attention 读取已生成 Token，再通过 Cross-Attention访问 Encoder 输出。Decoder 的 FFN 被 Sparse MoE 替代，由 Router 为每个 Token 选择少量专家，在不按相同比例增加激活 FLOPs 的情况下扩大总参数量。

图4：OneRec原始论文Figure 2。上半部分是Encoder–Decoder与Sparse MoE，下半部分是Iterative Preference Alignment。

4.2 Session-wise Generation

V1 没有把目标限制为“下一个视频”。论文将一次请求返回的5至10个视频视为一个 Session，并从真实日志中筛选高价值 Session，例如用户实际观看数量达到要求、总观看时长超过阈值，或发生点赞、收藏、分享等行为。

训练时，Session 中的视频依次展开为 Semantic Token。Decoder 在生成后一个视频时可以看到前面的生成结果，因此能够学习列表内部依赖。这个变化看似只是把单个目标扩成多个目标，实际改变了优化单位：模型学习的是用户会持续消费的一段内容，而非若干独立高分物品的拼接。

4.3 Iterative Preference Alignment

推荐请求通常只展示一个结果，无法像人工标注对话那样同时得到 chosen 和 rejected。V1 先用当前模型执行 Beam Search，得到多个候选 Session，再由个性化 Reward Model 打分。最高分结果作为 chosen，最低分结果作为 rejected。

DPO 损失为：

LDPO=−E[log⁡σ(βlog⁡πθ(S+∣Hu)πref(S+∣Hu)−βlog⁡πθ(S−∣Hu)πref(S−∣Hu))].\mathcal{L}_{\mathrm{DPO}} =-\mathbb{E}\left[ \log\sigma\left( \beta\log\frac{\pi_\theta(S^+\mid H_u)}{\pi_{\mathrm{ref}}(S^+\mid H_u)} -\beta\log\frac{\pi_\theta(S^-\mid H_u)}{\pi_{\mathrm{ref}}(S^-\mid H_u)} \right) \right]. LDPO​=−E[logσ(βlogπref​(S+∣Hu​)πθ​(S+∣Hu​)​−βlogπref​(S−∣Hu​)πθ​(S−∣Hu​)​)].

模型更新后重新生成候选，再构造新的困难负样本，形成 Iterative Preference Alignment。论文报告该模型部署在快手主场景后，Watch Time 提升1.6%。

4.4 技术报告补全了工业系统

2025年6月发布的技术报告把 OneRec 从论文方法扩展为完整系统。它详细介绍了协同增强多模态 Tokenizer、多尺度 Encoder、Decoder、Reward System、预训练与后训练、训练基础设施和在线推理。

图5：OneRec Technical Report Figure 2。传统系统的多阶段漏斗被单一Encoder–Decoder与Reward System替代。

报告给出了几个能说明工程价值的数据：训练和推理 MFU 分别达到23.7%和28.8%；相对传统复杂推荐管线，OPEX 降至10.6%；系统承担约25%的总QPS，并在快手和快手极速版上分别带来0.54%和1.24%的App Stay Time提升。报告中的这些指标与2月论文的1.6% Watch Time不是同一实验口径，不能直接横向比较。

5. OneRec-V2：把计算放到生成侧

5.1 V1的主要计算花在Encoder

V1 的上下文很长，目标 Session 很短。以长度512的上下文为例，V2报告指出，V1有97.66%的FLOPs用于上下文编码，真正用于目标生成的计算只有2.34%。即使把更多专家和参数加到 Decoder，大部分计算预算仍然被长序列 Encoder 消耗。

这使得 V1 的扩容方向出现偏差：模型参数增加了，负责最终推荐决策的生成部分却没有获得相称的计算。

5.2 Lazy Decoder-Only

V2 使用 Context Processor 将用户、上下文和物品路径整理成统一表示，再交给 Lazy Decoder。Lazy Decoder 保留 Self-Attention 和面向上下文的 Cross-Attention，但去掉 Cross-Attention 中重复的 WKW_KWK​、WVW_VWV​ 投影，并积极共享上下文 Key/Value。上下文不再像标准 Decoder-Only 模型那样在所有深层 Block 中反复执行完整 Self-Attention。

图6：OneRec-V2 Technical Report Figure 2。左侧是Lazy Decoder-Only，右侧把真实反馈接入偏好对齐。

报告给出的结果是：总计算量降低94%，实际训练资源降低90%；在相近计算预算下，参数规模从0.5B扩展到8B。0.1B到8B模型的收敛损失随规模平滑下降，说明新的计算分配方式更适合继续Scaling。

5.3 Duration-Aware Reward Shaping

直接使用播放时长作为奖励会偏爱长视频。同样看完80%，一个60秒视频天然比10秒视频产生更大的原始时长。V2先按视频时长进行对数分桶：

F(d)=⌊log⁡β(d+ϵ)⌋.F(d)=\left\lfloor\log_\beta(d+\epsilon)\right\rfloor. F(d)=⌊logβ​(d+ϵ)⌋.

对用户 uuu，将同一时长桶 bbb 中的历史播放时长组成集合 Pu,bP_{u,b}Pu,b​。目标视频 iii 的奖励取它在同桶历史中的经验分位数：

qi=∣{pj∈Pu,b∣pj≤pi}∣∣Pu,b∣.q_i= \frac{\left|\{p_j\in P_{u,b}\mid p_j\le p_i\}\right|} {\left|P_{u,b}\right|}. qi​=∣Pu,b​∣∣{pj​∈Pu,b​∣pj​≤pi​}∣​.

这相当于问：“对这个用户和这类长度的视频，本次观看表现处在什么水平？”V2把高分位样本作为正例，把 dislike 等显式负反馈作为负例，其余样本不参与策略更新。

5.4 GBPO稳定真实反馈强化学习

传统 PPO/GRPO 通过裁剪 Policy Ratio 控制更新幅度，但负样本仍可能产生不稳定梯度；Dual-clip 又会丢掉较多样本。V2提出 GBPO（Gradient-Bounded Policy Optimization），不直接丢弃越界样本，而是利用与当前策略概率相关的动态边界限制梯度，使负样本抑制更接近稳定的 BCE 梯度。

V2因此完成了两处实质变化：Backbone从重Encoder转向Lazy Decoder-Only，偏好信号从“只依赖Reward Model”转向Reward Model与真实用户交互结合。在线A/B实验相对V1带来0.467%和0.741%的App Stay Time提升，分别对应快手和快手极速版。

6. OneRec-Think：先分析兴趣，再生成物品

V1和V2主要在Semantic Token空间中预测。模型可能学会“哪些Token经常接在一起”，但推理过程不可读，也很难通过自然语言指令控制。OneRec-Think把自然语言Reasoning和Itemic Token放进同一次自回归生成：先产生兴趣分析，再生成目标物品。

图7：OneRec-Think Figure 2。三个阶段依次完成Itemic Alignment、Reasoning Activation和Reasoning Enhancement。

第一阶段是 Itemic Alignment。模型通过用户画像与Itemic Token交错数据、序列偏好建模、物品描述和通用语言数据，建立物品Token与语言语义之间的联系。

第二阶段是 Reasoning Activation。系统从用户历史中检索最相关行为，构造“为什么会喜欢目标物品”的推理监督。模型的生成过程变成：

τ∼Pθ(τ∣Hu,I),sn+1∼Pθ(sn+1∣Hu,I,τ),\tau\sim P_\theta(\tau\mid H_u,I), \qquad s_{n+1}\sim P_\theta(s_{n+1}\mid H_u,I,\tau), τ∼Pθ​(τ∣Hu​,I),sn+1​∼Pθ​(sn+1​∣Hu​,I,τ),

其中 III 是指令，τ\tauτ 是自然语言推理，sn+1s_{n+1}sn+1​ 是目标物品的Itemic Token。

第三阶段是 Reasoning Enhancement。推荐不存在唯一正确答案，同一个用户可能同时喜欢游戏、宠物和旅行。OneRec-Think使用面向推荐的奖励优化推理路径，并用 Think-Ahead 将较慢的兴趣分析提前计算，降低在线请求中的额外时延。论文报告线上App Stay Time提升0.159%。

7. OpenOneRec：开放推荐基础模型

OpenOneRec不只是“把V2代码开源”。它把问题从快手Feed中的端到端生成，扩展成Recommendation Foundation Model：同一个模型需要理解物品、执行多个推荐任务、遵循指令、生成推荐解释，并尽量保留通用LLM能力。

图8：OpenOneRec Technical Report Figure 2。Qwen3依次经过Itemic-Text Alignment、Co-Pretraining、SFT、On-policy Distillation和Rec-RL。

7.1 模型与数据

OpenOneRec建立在Qwen3上，开放1.7B和8B两种规模，每种又分Standard与Pro。Standard使用公开数据训练，报告中的预训练规模为32B Token、4130万样本；Pro使用更大规模工业语料，达到130B Token、1.791亿样本。

配套的RecIF-Bench包含约1.2亿次交互、20万用户，覆盖短视频、广告和商品三个领域。它将能力分为四层：Semantic Alignment、Fundamental Prediction、Instruction Following和Reasoning。评测对象由单一Recall指标扩展为物品理解、短视频/广告/商品推荐、交互式推荐、条件推荐和推荐解释。

7.2 预训练与后训练

预训练分两步。Stage 1扩充Qwen3词表，只训练新增Itemic Embedding与对应LM Head，使新Token先获得稳定表示；Stage 2进行全参数Co-Pretraining，将推荐领域数据与通用知识数据混合训练，把协同关系、物品语义和语言能力放入同一模型。

后训练包含三步：Multi-task SFT建立基本指令遵循；On-policy Distillation以原始Qwen3为Teacher，修复推荐预训练造成的通用推理退化；Rec-RL再优化推荐命中和生成质量。这个顺序反映了推荐基础模型的矛盾：推荐数据会增强专业能力，也可能挤压原有语言与推理能力，训练需要在两者之间反复校准。

8. OneReason：让Think模式真正服务推荐

OneRec-Think和OpenOneRec已经能生成自然语言推理，但OneReason报告指出一个反常现象：Think模式并不总是优于Non-Think。模型会写出流畅的兴趣分析，不代表它真正理解Itemic Token，也不代表分析与最终物品一致。

OneReason把问题拆成两个基础条件：

  • Perception：把Itemic Token准确映射到物品内容、属性和关系；
  • Cognition：把用户行为重新组织为兴趣点，并推断兴趣如何变化。
图9：OneReason Technical Report Figure 2。训练由多粒度预训练、推荐CoT SFT和四领域RL组成，评测覆盖R0到R3。

预训练数据按Token、Item、Relation和User四种粒度组织：Token粒度学习码字语义，Item粒度理解完整物品，Relation粒度学习物品之间的关系，User粒度学习长行为中的兴趣结构。

SFT任务被划分为R0到R3：R0 Perception负责语义落地；R1 Derivation推导物品关系；R2 Evolution分析兴趣随时间变化；R3 Recommendation完成单域与跨域推荐。推荐CoT也不再是自由发挥的长文本，而是围绕Persona Abstraction、Interest Expansion和Transition Inference组织。

RL阶段采用Specialize-then-Unify。模型先在视频、广告、直播和商品领域分别优化，再通过蒸馏或统一训练合并能力。这样做是因为不同领域的物品空间、序列长度和奖励密度差异很大，直接混合容易让某一领域主导梯度。OneReason还使用两阶段Rollout，让一条推理轨迹对应多个物品采样，摊薄推理成本并提高候选多样性。

OneReason把推荐推理的问题压缩得很具体：<think>里多写一段流畅文本并不会自动提高推荐效果，物品感知、兴趣抽象、推理轨迹和最终物品必须彼此一致。

9. 总结与展望

回看OneRec系列，技术演进可以归纳为三条线。

第一条是架构效率。V1用Encoder–Decoder统一召回与排序，并通过Sparse MoE扩大容量；V2发现长上下文Encoder占用了97.66%的计算，于是转向Lazy Decoder-Only，把更多预算放到生成决策上。

第二条是偏好信号。原始论文用Reward Model构造DPO偏好对，技术报告形成完整Reward System，V2进一步引入真实观看时长和显式负反馈。优化目标逐渐靠近实际用户行为，但短期反馈与长期价值之间仍有距离。

第三条是能力范围。OneRec-Think让模型先分析再推荐，OpenOneRec开放跨领域基础模型与评测，OneReason继续补强Itemic感知和推荐CoT。模型的目标从“生成正确物品”扩展为“理解物品、理解用户、遵循指令并解释推荐”。

接下来的难点也很具体。

Semantic ID需要面对高速变化的物品库。重新聚类会导致旧Token语义漂移，增量更新又可能破坏码本平衡。生成结果还必须满足去重、安全、广告负载、作者生态和内容多样性等硬约束，纯概率生成很难独自承担所有规则。真实反馈强化学习则要处理曝光偏差、策略变化和探索风险，尤其不能把短期观看时长简单等同于长期满意度。

OneMall、OneLoc、OneSug等工作已经把端到端生成扩展到电商、本地生活和搜索场景。更现实的落地形态可能是混合系统：生成模型承担统一表示、候选生成和列表级决策，外部检索、约束解码与业务规则负责精确控制。沿着OneRec系列，可以看到三个已经成形的接口：统一Token、可Scaling的Backbone，以及直接作用于推荐结果的策略优化闭环。
